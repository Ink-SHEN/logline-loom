## 一、事故：创空间连不上 Spark，而所有巡检都是绿的

09-12 从创空间侧回看链路，发现后端不可达。排查结论不是「连不上」，是**早就连不上**：

| 证据 | 数值 |
|---|---|
| `~/natapp/natapp.log` 总行数 | 22173 |
| 其中 `status=online` | **1 次**（09-08 14:43:18） |
| 其中 `status=reconnecting` | **7198 次**（retry=30s） |
| 7198 × 30s | ≈ 60 小时 = **09-09 20:04 → 09-12 08:04** |
| 最后一次成功承载流量 | `09-09 20:04:00` |

唯一错误只有一种：`control recovering from failure dial tcp 127.0.0.1:442: connect: connection refused`
——客户端在往**本机回环**拨控制连接。

### 根因：`*.natappfree.cc` 整个通配符被解析到 127.0.0.1

| 域名 | 本机 | 8.8.8.8 | 223.5.5.5 | 114 | AliDNS DoH | 腾讯 doh.pub |
|---|---|---|---|---|---|---|
| `ncafd2da.natappfree.cc` | 127.0.0.1 | 127.0.0.1 | 127.0.0.1 | 127.0.0.1 | 127.0.0.1 | 127.0.0.1 |
| `server.natappfree.cc`（客户端要连的控制服务器） | 127.0.0.1 | 127.0.0.1 | 127.0.0.1 | 127.0.0.1 | 127.0.0.1 | 127.0.0.1 |

关键在第二行：**连客户端自己要连的控制服务器域名都是回环地址**，所以它只可能往回环拨号。
换 DNS 无用（权威侧就是这个结果），重启客户端也无用。natapp 自己的网络诊断在 09-09 20:06
也打印过 `解析 ncafd2da.natappfree.cc → 127.0.0.1 [警告: 可能是异常地址]`。**这条隧道判死。**

### 真正该被记住的不是 natapp 挂了，是我们的巡检漏诊

`loom_watch.py`（v1）每 5 分钟写一行「上报成功：已上报」——它只验证**创空间接口返回了 200**，
**从不检查隧道本身**；`current_url()` 又只是从日志里抄最后一次 `Tunnel established at`，
地址死了照样返回旧域名。结果：**隧道断了 2.5 天，日志一路绿灯，团队侧零告警。**

> 教训：**「进程在」和「接口返回 200」都不等于「公网可达」。** 巡检必须从公网侧真打一次。

## 二、换隧道：三条路，为什么选 cloudflared

前提两条硬约束：① `106.13.186.155` 是比赛侧托管的云节点，**安全组我们改不了**；
② Spark 在 `192.168.110.68/24` 内网、出口 `180.165.35.34`，**没有任何公网入向**。
所以只有两类出路：**从 Spark 主动出网建隧道**，或**借已开放的端口做 SSH 转发**。

| 路径 | 结果 | 淘汰/采用原因 |
|---|---|---|
| A. 让跳板机放行 6200，复用已有 frps | ❌ 淘汰 | 不能改安全组。跳板机放行端口仅 `6050–6102` + `6104/6108/6110/6117/6119` + `7000/8080/9100`，**全部被现有映射占满**；frps 上空闲的 `6200/8000/9001…` 都不在放行段内 |
| B. 复用同事 xsuper 的 frpc 配置加一条映射 | ❌ 淘汰 | `/home/xsuper` 权限 `drwxr-x---`，`Developer` 在 sudo 组但**需密码**，frpc 也没开管理接口 |
| C. **SSH 直连兜底**：借已开放的 `6068 → Spark:22`，用 `direct-tcpip` 通道打进 `127.0.0.1:8188` | ✅ 实测可用，留作兜底 | 零新端口、零第三方。实测：无 token 401 / 带 token 200（1351B）/ `/batch/nonexistent` 404。**代价是创空间要加 paramiko + 新增 SSH 口令 secret**，评审前不宜动提交物 |
| D. **cloudflared quick tunnel** | ✅ **采用** | 纯出网（QUIC/UDP 7844 到 Cloudflare edge），不需要安全组、不需要任何人配合；**创空间一行代码都不用改**——它本来就是「候选地址 + 探活」的纯 URL 驱动模型，换域名能自愈 |

选 D 的决定性理由：**创空间的集成面是零**。`space/tunnel.py` 早已是
「secrets 硬地址 → Spark 上报地址 → 上次成功地址」三档候选 + 逐个探活，
换隧道供应商只需要 Spark 上报一个新 URL。相比之下 C 要动提交物的代码和依赖。

## 三、落地

### 1. `loom_watch.py` v2：先真探活，再决定要不要上报

- 隧道进程换成 `cloudflared`，域名从 `cloudflared.log` 解析（`https://*.trycloudflare.com`）；
- **每轮先 `probe()` 真打一次 `{url}/system_stats`**，分三档判定：
  - `ok`（HTTP 200）→ 才写 `tunnel_url`、才上报；
  - `auth`（401/403）→ 地址有效但两端 token 不一致，记警告仍上报；
  - `down` → 记「隧道不可达：<原因>」，**不把死地址报给创空间**，连续 3 次失败即重启 cloudflared（重启会换域名）；
- 新增 `tunnel_state.json` 落盘每次探活结论（`loom_status.sh` 直接读它）；
- 状态没变化时最多 30 分钟写一行心跳，避免日志刷屏。

### 2. 运维脚本三件套同步

- `loom_up.sh`：第 3 步改 cloudflared，起来后等域名分配（最多 60s）并打印；
- `loom_health.sh`：第 3 步从「查进程」改成 **查进程 + 公网真探活**，
  `401/403` 视为「通但 token 不匹配」告警，其余非 200 一律重置 cloudflared 并打印新域名；
  汇总行 `natapp=` → `tunnel=`；
- `loom_status.sh`：换成 cloudflared 段，同时打「带 token（期望 200）」和「无 token（期望 401）」两次，
  并把 `tunnel_state.json` 的上次结论贴出来；末尾单列一节标注 natapp 已废弃。

### 3. natapp 退役

进程停掉，`loom_up.sh` / `loom_health.sh` 不再拉起它（解析函数保留备查）。

## 五、遗留与风险

1. **quick tunnel 无 SLA**：Cloudflare 自己声明 account-less tunnel「no uptime guarantee」。
   缓解是「真探活 + 连续失败重启 + 换域名自动重报」；真要长期稳定，应换成命名隧道（需 Cloudflare 账号）。
2. **SSH 直连兜底已实测但未接入**：路径 C 是唯一不依赖第三方的方案，
   接它需要动创空间代码（paramiko + secret）。**评审前不动提交物**，留作应急。
3. **评审期节点归属待确认**：若这台 Spark 是比赛方提供的节点，需确认 09-15→09-18 评审窗口内不回收/不重装。
   这是本方案唯一的「生死项」。
4. 跳板机上我们自己的那个 frpc 仍在跑（映射 6200 无法绑定，纯空转），保留是因为
   **一旦哪天放行 6200 就能立刻拿到固定地址**；不占资源，需要时可 `pkill -x frpc`。
