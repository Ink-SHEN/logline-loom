# 创作手记 · 09-13（Day 9·下午）⑤ 生成站改为「可插拔模型 API 接口」——创空间自包含化，Spark 侧隧道一并退役

> 衔接同日上午那篇《隧道供应商替换》（`2026-09-13-tunnel-switch.md`）。上午刚把 natapp 换成
> cloudflared、把「真打公网」的探活补上；**下午架构就变得更简单了**——决定创空间不再远程回源
> 本机生成，⑤ 站改成一层可插拔的模型 API 接口。这篇记的是为什么改、改成什么样、怎么验证的。

## 一、为什么改

上午的方案有一个绕不开的前提：**Spark 上必须常驻一个公网入口**。而这个前提有三个坑：

| 坑 | 具体表现 |
|---|---|
| 节点不是我们的 | `106.13.186.155` 是比赛侧托管的云节点，安全组改不了；Spark 本身无公网入向 |
| 入口不稳定 | quick tunnel 无 SLA（Cloudflare 自己声明 account-less tunnel 无可用性保证） |
| 节点存续不可控 | 这台 Spark 09-15→09-18 评审期内是否仍归我们使用，**没有技术手段能兜底** |

也就是说：**评审期一旦节点被回收或断网，创空间就退化成「只能放示例素材」**。
把出片能力绑在一台不归自己管的机器上，是整条链路上最大的单点。

于是改设计：**创空间自己把「生成」这件事抽象成一个接口**，谁来实现接口都行——
今天可以是任意第三方视频生成 API，明天可以换另一个模型，后端换了创空间一行代码都不用动。

## 二、改成了什么：接口契约 v1

`space/generate.py` 现在只有两件事：把 ④ 的 c04 生成请求 POST 出去、把任务状态 GET 回来。

| 动作 | 请求 | 期望响应 |
|---|---|---|
| 提交 | `POST {LOOM_GEN_API_URL}/generations` | `{"task_id": "…", "status": "queued", "eta_seconds": 300}` |
| 查询 | `GET {LOOM_GEN_API_URL}/generations/{task_id}` | `{"status": "succeeded", "video_url": "https://….mp4"}` |

设计上刻意只提**一条硬要求**：模型侧能返回一个可播放的 mp4 URL。同步还是异步、有没有进度、
支不支持 seed，全是可选的——同步后端在提交响应里直接给 `video_url` 会被自动识别为已完成。
这样接入门槛足够低，任何一家视频生成 API 都能接。

**三种状态，界面永远说真话**（这是这条设计的核心，不是补丁）：

| 状态 | 条件 | 界面表现 |
|---|---|---|
| 已接入 | 配了 `LOOM_GEN_API_URL` | 真提交，给任务 ID，可查、可取回成片 |
| 接口就绪 | 没配 URL | 明说「等待接入模型」；④ 的生成请求照常产出；**不拿示例素材冒充本次生成** |
| 参考回放 | `LOOM_GEN_BACKEND=replay` | 播放 `space/fallback/` 往期成片，恒标注「非模型生成」 |

这条「宁可说没接上，也不假装生成了」的口径，和上午那篇的结论是同一条：
**界面上说的必须和实际发生的一致。**

## 六、代价与遗留（如实记）

1. **现在创空间里出不了片**：⑤ 站界面会诚实地显示「等待接入模型」。这是这次改动的**已知代价**，
   换来的是一条不会因外部节点失效而崩掉的链路。要让它出片，两条路：
   - 接一个满足契约的视频生成 API（配 3 个环境变量，**不改代码**）；
   - 或临时用 `LOOM_GEN_BACKEND=replay` 展示产物形态（界面会标注是参考回放，不是本次生成）。
2. **`space/fallback/` 的 4 段素材仍留在仓库**：它们现在的定位是「⑤ 站产物形态预览」，
   不再是「后端不可达时的替代品」。`index.json` 的 note 措辞已同步。
3. **`workflows/node_id_map.json` 与 T2V workflow 仍在**：它们服务于 c04 契约里的
   `workflow.node_ids` 字段（契约本身没改），只是 ⑤ 站不再拿它去拼 ComfyUI 图。

## 七、这次改动的自我复核

| 我做的判断 | 依据 | 有没有可能是错的 |
|---|---|---|
| 创空间不该依赖本机节点 | 节点归属、评审期存续都不可控；无技术兜底 | 若评审期节点稳定且允许常驻服务，这条架构其实也能用——但那是「赌」，不是「设计」 |
| 接口最小硬要求定为「返回可播放 mp4 URL」 | 这是唯一所有视频生成服务都能满足的共性 | 若某服务只返回裸字节流或需要轮询文件系统，得再加一个适配层 |
| 删掉 `tunnel.py` 而不是留着 | 留着会被误读为「还有隧道这条路」，且 `generate.py` 的冒烟断言会失败 | 若明天又要恢复隧道，从 git 历史取回即可（09-13 上午那篇手记里有完整设计与实测数据） |

# 补充（同日晚）：⑤ 支持「界面运行时接入」，并把「只发 S001」补成逐镜全下发

> 傍晚的追加改动。上面那版虽然把接口抽象出来了，但要真出片仍得**改环境变量 + 重新部署**，
> 门槛偏高；而且 ⑤ 站当时只把 `genreq_first`（S001）发出去，其余镜头停在 ④ 的产物里。
> 这两点一并补上。

## 一、改了什么

| 维度 | 之前 | 现在 |
|---|---|---|
| 谁填接口信息 | 只有环境变量（只有我能配，改完还得重建创空间） | 「⑤ 生成接口」页签顶部有面板：**地址 / Key / 模型名 / 后端 / 等待上限**，填完点「开始生成」当场跑通 ①→⑤ |
| 下发几个镜头 | 只发 S001（`genreq_first`） | **逐镜各一份独立任务**，每镜带自己的 seed / prefix / 时长 |
| 拿不拿结果 | 提交即返回，靠人手动粘任务 ID 去查 | 有界轮询（默认 300 秒，面板可调），取回的成片直接进产物区 |
| 产物区标注 | 只有「示例素材」 | **★ 本次生成** / **参考回放（非模型生成）** / **示例素材（非本次生成）** 三态分开标 |

优先级：**界面填的 > 环境变量**。留空则回落环境变量，两者都不配就是「接口就绪，等待接入模型」。

## 二、Key 怎么处理（特意想清楚的一层）

界面是公网的，Key 会从访客浏览器流到容器。所以：

- **不落盘**：`GenSettings` 是不可持久化的值对象；任务表只记 `endpoint`，且**只存主机名**
  （`urlsplit().netloc`，剥掉 path / query / 凭据）
- **不进日志**：`GenSettings.__repr__` 把 Key 掩成 `***`，任何 `%r` / f-string 都打不出来
- **不跨会话**：只作为本次调用的参数往下传；**后端实例自己不持有配置**，多个使用者不会互相串
- 输入框用 `type="password"`，界面明写「只活在你这一次请求里，刷新即失效」

## 三、顺带补的一层安全校验

创空间是公开服务、接口地址由任意访客填 —— 不能让它替调用方去探内网或云元数据端点。
`generate.check_endpoint()` 两层校验：字面 IP 直接对**拒答名单**（环回 / 私网 / 链路本地 /
CGNAT / IPv6 本地 / `metadata.google.internal` 等）判；域名再 `getaddrinfo` 解析一次判
（防 DNS 指向内网）。本地调试跑 `127.0.0.1` 时用 `LOOM_GEN_ALLOW_PRIVATE=1` 放行。

## 五、踩到的两个坑（都是自己造的，记下来）

1. **生成器 yield 了同一个可变 dict**：`run_all_iter` 里反复 `state.update(...)` 后直接 `yield state`，
   调用方 `list()` 收下来的 N 个快照**全部指向最终态**——界面上表现为进度不推进。
   改成 `yield _snapshot(state)`（深拷 `shots` / `videos`）后正常。
2. **回放模式差点被标成「本次生成」**：`ReplayBackend` 返回的也是 `status=succeeded` + 一个本地路径，
   若按 `succeeded` 无脑标 ★，就等于**拿往期成片冒充本次生成**，直接违反这个项目「三态如实」的原则。
   现在按后端的 `replay` 标记分流措辞，并加了两条断言（含「回放产物不得出现 ★」）。
3. **`query` 侧的 SSRF 通道**（**线上活体探测才发现**，本地测试捞不到）：
   `HttpModelAPI.submit` 加了 `check_endpoint`，但 `query` 忘了加。线上实测用 `query_generation`
   填 `http://127.0.0.1:8000/v1`，容器**真的去连了**（回 `Connection refused`）；
   而错误信息会把内网服务的响应带回界面 —— 这是一条可被利用的 SSRF 通道。已补上同一道校验。
   > 教训：**校验要加在「所有会对外发请求的出口」上，不是加在「提交」上**。
   > 单测只覆盖了 `submit` 路径，所以本地全绿；是线上拿真地址试出来的。
4. **把「填错了」误报成「没接模型」**：地址填了但不可用时，`run_c05` / `run_all_iter`
   只回通用的「⑤ 生成接口已就绪，等待接入模型」。使用者填错地址却被告知「还没接模型」，
   等于把人往错方向指。新增 `_unavailable_note()` 区分两种情形：没填 → 等待接入；
   填了但不可用 → 明说地址有问题，并带上 `check_endpoint` 给出的具体原因。
5. **参考回放的 task_id 同秒撞车**：原来用秒级时间戳，8 个镜头在同一秒下发只出 2 个不同 ID，
   任务表互相覆盖。改成「镜头分区 + 单调序号」（`replay-loom-S001-001`）。
6. **产物区重复列同一素材**：按路径去重后才正常。

## 六、还没做的

- **线上没拿真实模型端点验证过**：手上没有可用的公网生成 API。线上验的是
  「面板留空 → 如实说等待接入」与「后端 replay → 逐镜下发 + 标注参考回放」两条路；
  真出片那条路由 `test_ui_e2e.py` 的本地假服务证明（契约完全相同，只是换了 host）。
- 长期接入建议仍走环境变量；界面那套是给评审/试用用的。

## 七、部署终验改成「不依赖 LLM」的活体探测

第一次终验跑整条 `run_pipeline` 时，**卡了 15 分钟没出结果**。原因不在本轮改动：
①–④ 要连调 LLM，④ 是**逐镜 8 次**调用，而 `llm.chat` 最坏会做 3×300s 重试；
容器冷启动后端点慢一点，整条链路就不可控了。

所以终验改用 `tmp/deploy_and_probe.py`：部署完直接打创空间暴露的 gradio 端点，
**全部秒级返回、且都落在本轮改动的关键路径上**——

| 探测 | 验什么 |
|---|---|
| `probe_gen` × 5 组地址 | 面板取值路径 + 地址校验（空/环回/元数据/非 http/私网） |
| `query_generation` | 查询侧是否也过校验（就是靠这条捞出上面那个 SSRF 通道） |
| `GET /config` | 面板组件是否注册、`run_pipeline` 入参出参数、API 面是否干净 |
| `gen_interface_status` 不在 API 面 | 反向断言：`api_name=False` 确实把它挡掉了 |

> 这一条能推广：**验证要挑「与本次改动强相关、又不依赖外部不确定性」的入口**。
> 拿整条链路去验一个入口改动，是把外部服务的抖动算到自己头上。

# 补充（同日晚·第二轮）：把「运行时长不可控」真的修掉，而不是绕开

第七节只把**验证**绕开了——产品侧那条链路仍然是小时级不可控。被追问后决定正面修。

## 一、先把耗时结构量出来

| 环节 | 位置 | 倍数 |
|---|---|---|
| ③ 要求镜头数 | `app.py` | 6–8 个 |
| ④ 逐镜各调一次 Agent | `pipeline.build_all_gen_requests` 的 `for shot in shots` | ×8 |
| `call_agent` = 1 次 + `llm_fix_rounds`(3) 轮纠正 | `pipeline.call_agent` | ×4 |
| `llm.chat` 内部重试 `retries=2` | `space/llm.py` | ×3 |
| 单次 HTTP 超时 `llm_timeout()` | `space/config.py` | 300s |

⇒ ④ 单独最坏 `8 × 4 × 3 × 300s ≈ 8 小时`；而 `run_pipeline` **原本没有任何时间上界**。

## 二、加了哪两道闸门（关键：默认零副作用）

1. **`LOOM_RUN_BUDGET_SECONDS`**（默认 1200 秒 = 20 分钟）——整条 ①→④ 的墙上时间预算。
2. **`LOOM_GEN_MAX_SHOTS`**（默认 8）——**这里发现它原本是个死配置**：只在 `config.py`
   定义、在文档表里写了一句，全仓库**没有任何调用**。文档写着「本次最多下发几个镜头」，
   实际不生效。现在接到 `build_all_gen_requests` 上了。

**为什么不会有副作用（这是设计时最在意的一点）**：

- 默认预算 1200 秒，而正常一整片 3–5 分钟 → **默认配置下永远碰不到这条线**；
- 默认镜头上限 8，而 ③ 只被要求产 6–8 个镜头 → **默认等于不设限**；
- 单次调用超时取 `min(LOOM_LLM_TIMEOUT_MS, 剩余预算)`，预算充裕时取到的就是 300 秒，
  **与加闸门之前一字不差**。这条有断言守着（e2e `5c`：`300 vs 300`）。

## 三、预算到点后的处理：明说，不静默

- 检查点放在**「开始每一镜之前」**，不是中途打断——发出去的那次调用不拦腰截断，
  只是不再开新的。这样既有硬上界，又不会把一次本来能成的调用切坏。
- 剩余镜头**保留占位**（不静默丢弃），`gen` 留空，`note` 写明
  「⏱ 超出本次运行预算（1200 秒），未生成」；
- ④ 的 summary 里逐条写出「哪几个镜头、为什么没产出」；
- ⑤ 的状态表把这类镜头标 `skipped`，并**沿用 ④ 的说明**作为原因——
  而不是笼统一句「④ 的 c04 里没取到 prompt」（那会把「预算用尽」误报成「④ 坏了」）。
