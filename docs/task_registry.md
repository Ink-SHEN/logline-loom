# 生成任务登记表

每一次提交到 ComfyUI 的生成都要在这里留一行。**先登记再提交**，
这样别人 `GET /queue` 看到陌生任务时能知道是谁的、在跑什么。

维护人：C。任何人都可以追加自己的行。

---

## 一、为什么要登记

三个具体理由，都不是为了「留痕好看」：

1. **ComfyUI 会缓存完全相同的输入，0 秒返回旧文件。**
   没有登记表，你无法判断拿回来的 mp4 是新生成的还是上一次的。
   表里的「缓存命中节点数」这一列就是干这个的——**接近节点总数就说明输入撞了**
2. **耗时预算要靠真实数字，不能靠猜。**
   本文件下方那 6 条实测记录，直接推翻了「一个镜头要跑半小时」的假设，
   把整片 GPU 预算从「跑不完」改成「5 小时够用」
3. **`prompt_id` 是唯一能反查完整参数的东西。**
   成片里任何一个镜头出问题时，靠它能 `GET /history/<prompt_id>`
   拿回当时提交的整张图，包括种子

## 二、表格模板

复制这一段往上追加：

```markdown
| 2026-09-XX | 谁 | S001_c00 | T2V | <prompt_id 前 8 位> | shots/S001_c00 | <seed> | 5.0 | 0.4 | 实测秒数 | 缓存命中/总节点 | 产物文件名 | pass/fail/待检 | 备注 |
```

列的含义：

| 列 | 填什么 | 注意 |
|---|---|---|
| 日期 | 提交日期 | |
| 谁 | A / B / C | |
| 候选 ID | `S001_c00` | 与 c05 契约的 `candidate_id` 格式一致：`^S[0-9]{3}_c[0-9]{2}$` |
| 类型 | T2V / I2V / R2V | **R2V 要在备注里写明是谁切了权重** |
| prompt_id | 前 8 位即可 | 完整值在 `shots/<候选>/meta.json` 里 |
| filename_prefix | `shots/S001_c00` | 契约要求 `^shots/S[0-9]{3}(_c[0-9]{2})?$`。**不要用 ComfyUI 默认的 `video/MiniMax_H3`**，那个前缀会让所有产物互相覆盖 |
| seed | 整数 | 多候选必须递增，见 `docs/gpu_protocol.md` 规则 2 |
| 时长(秒) | 4–15 的浮点 | |
| megapixels | 通常 0.4 | 提到 1.0 会让耗时翻数倍 |
| 实测秒数 | `execution_success - execution_start` | 毫秒差 / 1000 |
| 缓存命中 | `len(execution_cached.nodes)` / 总节点数 | |
| 产物 | 文件名 | 在 `outputs["<节点ID>"]["images"][0]["filename"]`。**视频也叫 `images`** |
| 质检 | pass / fail / 待检 | fail 要写明失败项，并登记重试那一条 |

## 三、已有记录

以下 6 条是从节点 `GET /history` 直接读出来的**真实运行记录**，
不是示例数据。它们是本仓库所有耗时结论的唯一依据。

时间为节点侧记录，`prompt_id` 取前 8 位：

| 日期 | prompt_id | 类型 | filename_prefix | 时长(秒) | 实测秒数 | 缓存命中/总节点 | 产物 |
|---|---|---|---|---|---|---|---|
| 09-03 14:50 | `c59bbfa9` | T2V | `video/MiniMax_H3` | 5.0 | **636.5** | 0 / 23 | `video/MiniMax_H3_00001_.mp4` |
| 09-03 21:53 | `00d23349` | T2V | `video/MiniMax_H3` | 5.0 | **1.4** | 20 / 23 | `video/MiniMax_H3_00002_.mp4` |
| 09-03 21:54 | `8ab08f74` | T2V | `video/MiniMax_H3` | 5.0 | **0.0** | 21 / 23 | `video/MiniMax_H3_00002_.mp4` |
| 09-04 19:16 | `d8285ce4` | I2V | `test-shot` | 5.0 | **217.6** | 9 / 24 | `test-shot_00001_.mp4` |
| 09-04 19:21 | `603dfc2c` | I2V | `test-shot` | 5.0 | **0.0** | 24 / 24 | `test-shot_00001_.mp4` |
| 09-04 19:24 | `8716f0bb` | I2V | `shot1` | 4.0 | **126.6** | 15 / 24 | `shot1_00001_.mp4` |

耗时统计：最短 0.0 s，最长 636.5 s，平均 163.7 s（6 次）。

### 从这 6 条能读出什么

**① 冒烟测试状态：T2V 与 I2V 已通过，R2V 一次都没跑过。**

三条 T2V、三条 I2V，`status_str` 全是 `success`，都有产物文件。
也就是说这两条链路的**出片能力已经被证实**，剩下的只是质量调优。

**R2V 完全没跑过**，而它偏偏是三条里风险最高的：
需要把 FL2VA 换成 Ref2VA（重载 21 GB+）、需要先把参考图 `POST /upload/image`、
节点 ID 是纯数字（和 T2V/I2V 的复合 ID 不同）。
**这是当前最大的未知项，应该排在最前面做掉，不要留到后面。**

**② 第 2、3、5 条是缓存命中，不是「跑得很快」。**

`00d23349` 与 `8ab08f74` 的产物文件名和第 1 条完全一样
（都是 `..._00002_.mp4`），`603dfc2c` 也一样。耗时 0.0–1.4 秒。
这就是 `docs/gpu_protocol.md` 规则 2 的实证：**输入不变就拿回旧文件**。
如果当时没看缓存命中数，很容易误以为「生成只要 1 秒」。

**③ 冷启动惩罚约 7 分钟，但这个数字是估算。**

636.5 s 那条是首次运行（0 / 23 缓存），包含了权重加载。
但它和后面几条不是同一个工作流，差值里混进了工作流本身的差别，
所以只能说量级是「多花约 7 分钟」，不能当精确常数用。

**④ 片长与耗时不成线性。**

4 s → 126.6 s，5 s → 217.6 s。时长只多 25%，耗时却多 72%。
说明固定开销（文本编码、VAE 解码、音频分支）占比很大，
**短片长更划算**，能用 4 秒表达的镜头不要凑到 5 秒。

**⑤ 前 5 条用的是 ComfyUI 默认前缀，这是要避免的反面例子。**

`video/MiniMax_H3`、`test-shot`、`shot1` 都是随手设的。
后果是 `00d23349` 和 `8ab08f74` 指向同一个文件，谁覆盖谁说不清。
正式生产必须用契约规定的 `shots/S001_c00` 格式，
一个候选一个独立前缀，永不互相覆盖。

## 四、怎么把这张表自动化

手工登记一定会漏。B 在写生成 Agent 时，让它顺手做两件事：

1. 提交成功后立刻写 `shots/<candidate_id>/meta.json`（模板见 `shots/README.md`）
2. 任务完成后从 `/history/<prompt_id>` 读回时间戳与缓存节点数，
   追加一行到本文件

第 2 步的解析要注意 `outputs` 的结构，实测长这样：

```python
outs = record["outputs"]
files = []
for node_id, block in outs.items():
    for item in block.get("images", []):      # 视频也在 "images" 下，且是列表
        if isinstance(item, dict) and "filename" in item:
            files.append((node_id, item["filename"], item.get("subfolder", "")))
```

按 `isinstance(block, dict) and "filename" in block` 判断会**全部漏掉**
（这是实际踩过的坑），因为 `filename` 在列表里的字典中，不在 `block` 本身。
