# GPU 排队协议

本文是节点使用的唯一约定。三个人共用一台 DGX Spark、一个 ComfyUI 实例，
不写清楚会互相覆盖任务、反复重载权重，或者拿到一个 0 秒返回的旧视频还以为生成成功了。

---

## 一、先纠正一个常见误解

**排班要排的不是「谁用 GPU」，而是「任务以什么顺序进队列」。**

ComfyUI 的 `/queue` 本身就是严格 FIFO 串行的：同时 POST 三个任务，
它也会一个跑完再跑下一个，**不存在两个人抢同一块卡把显存打爆的情况**。

真正会出问题的是**顺序**。因为 ComfyUI 是按工作流里声明的模型来加载权重的，
队列里如果 T2V、R2V、I2V 交替出现，它就得反复卸载 / 重载 21 GB 以上的权重。
按下面的实测数据，一次冷启动的代价约等于 3–5 个热态镜头。

---

## 二、为什么这台机器特别怕反复重载

DGX Spark 是 **128 GB LPDDR5x 统一内存**，CPU 与 GPU 共享同一个物理池。
`GET /system_stats` 的实测值（2026-09-04，节点上有一个任务在跑时采集）：

| 字段 | 字节 | 约合 |
|---|---|---|
| `ram_total` | 128501485568 | 119.7 GiB |
| `ram_free` | 50752606208 | 47.3 GiB |
| `vram_total` | 128501485568 | 119.7 GiB（**与 `ram_total` 相同**） |
| `vram_free` | 13753201847 | **12.8 GiB** |
| `torch_vram_total` | 66068676608 | 61.5 GiB |
| `torch_vram_free` | 2706539703 | 2.5 GiB |

设备名：`cuda:0 NVIDIA GB10 : cudaMallocAsync`。

三个要点：

1. **`vram_total` 与 `ram_total` 报同一个数**，这是统一内存的正常表现，不是 bug。
   这台机器上 `nvidia-smi` 看不到独立显存占用，要看 `free -h`。
2. **PyTorch 已经吃掉 61.5 GiB**，而 `vram_free` 只剩 12.8 GiB。
   这不是泄漏，是启动参数 `--highvram` 的效果：它让模型**常驻不卸载**，
   换来的是热态生成不用每次重新加载权重。
3. 正因为常驻，**FL2VA（T2V / I2V 用）与 Ref2VA（R2V 用）装不下同一份**。
   两份权重加文本编码器 / VAE 超过可用余量，切换必然触发卸载 + 重载。

## 三、三条规则

### 规则 1：按工作流类型分批入队

**不要**这样排队：

```
S001(T2V) → S002(R2V) → S003(I2V) → S004(R2V) → ...
```

**要**这样：

```
[全部 T2V]  →  [全部 I2V]  →  [切换权重]  →  [全部 R2V]
```

T2V 与 I2V 用的是**同一份** FL2VA 权重，它们之间切换不需要重载，可以混排。
只有进出 R2V 批次时才需要换权重，**整场拍摄尽量只换一次**。

实操上，分镜 Agent（c03_shotlist）在产出镜头表时就要按这个顺序编号，
生成 Agent 按 `shot_id` 顺序提交即可，不需要额外的调度器。

### 规则 2：出多个候选必须换种子

ComfyUI 有输入缓存。**输入完全相同的两次提交，第二次 0–1.4 秒返回，
并且返回的是同一个旧文件**（实测见 `docs/task_registry.md` 里 `00d23349…` 与
`8ab08f74…` 两条，产物文件名与首跑一致）。

所以「一个镜头出 3 个候选」的正确做法是：

```python
base_seed = 20260904
for i in range(3):
    wf[NODE_IDS["noise_seed"]]["inputs"]["noise_seed"] = base_seed + i
    wf[NODE_IDS["filename_prefix"]]["inputs"]["text"] = f"shots/S001_c{i:02d}"
```

`noise_seed` 与 `filename_prefix` **两个都要改**：
只改种子会覆盖同名文件，只改前缀会拿回同一个视频。

节点 ID 从 `workflows/node_id_map.json` 查，**不要在代码里硬编码**。

### 规则 3：素材先上传，再引用

`LoadImage.image` 是枚举输入，**只能填节点上真实存在的文件名**，
填一个本地路径会在提交时直接报 `Value not in list: image`。

R2V 的参考图流程：

```bash
# 1. 上传
curl -F "image=@ref.png" -F "overwrite=true" http://127.0.0.1:8188/upload/image
# 2. 用返回的 name 填进工作流
```

上传后记得把文件名登记进 c04 的 `assets.ref_images[].node_filename`，
否则下一个人不知道这个素材是谁传的、对应哪个镜头。

## 四、实测性能基线

数据来源：ComfyUI `GET /history` 每条记录里 `status.messages` 的
`execution_start` 与 `execution_success` 两个 epoch 毫秒时间戳相减。
用时间戳差值而不是墙钟，是为了不受时区与本机时钟影响。

`megapixels = 0.4`（16:9 下约 848×480），未启用 turbo LoRA：

| 场景 | 时长设定 | 实测耗时 | 缓存命中 |
|---|---|---|---|
| T2V **冷启动**（首次，含权重加载） | 5 s | **636.5 s** | 0 / 23 节点 |
| I2V 热态 | 5 s | **217.6 s** | 9 / 24 节点 |
| I2V 热态 | 4 s | **126.6 s** | 15 / 24 节点 |
| 输入完全相同（命中缓存） | — | **0–1.4 s** | 21–24 节点 |

由此得到两个可用数字：

- **热态单镜头：约 2–4 分钟**（4–5 秒片长）
- **冷启动惩罚：约 7 分钟**（估算值。636.5 s 那次与后面几次不是同一个工作流，
  差值里混进了工作流本身的差别，所以只能说量级）

片长与耗时的关系：4 s → 126.6 s，5 s → 217.6 s。**不是线性**，
因为固定开销（编码、VAE 解码、音频分支）占比很大，短片长时更划算。

## 五、整片的 GPU 预算

按 25 个镜头、每镜头 3 个候选、`megapixels = 0.4` 估算：

| 方案 | 估算 GPU 时间 |
|---|---|
| 75 次热态生成 × 约 3 分钟 | **≈ 3.8 小时** |
| 加 30% 重试（质检不过重来） | **≈ 5 小时** |
| 若提到 `megapixels = 1.0` | ≈ 10–15 小时（未实测，按面积线性外推并留余量） |
| 若启用 turbo LoRA | ≈ 4–6 小时可压到 1–2 小时（LoRA 加速比 2.5× / 5× 为官方标称，本机未实测） |

**结论：GPU 时间不是瓶颈。** 5 小时对一个 5 天的赛程来说很宽裕。
真正的瓶颈是**契约没冻结导致返工**，以及**人工关口排队等人裁决**。

## 六、turbo LoRA（加速开关，尚未实测）

节点上两份加速 LoRA 都在位：

| 文件 | 作用 | 标称加速 |
|---|---|---|
| `loras/minimax_h3_fl2v_turbo_8step_v1.0_comfyui_bf16.safetensors` | T2V / I2V，20 步 → 8 步 | ≈ 2.5× |
| `loras/minimax_h3_ref2v_turbo_4step_v0.1_comfyui_bf16.safetensors` | R2V，20 步 → 4 步 | ≈ 5× |

启用方式是把工作流里一个 `PrimitiveBoolean` 翻成 `true`，
下游 `ComfySwitchNode` 会同时换掉模型与步数。**不要手动改步数**，
那样只改了一半，出来的画面会崩。

建议用法：前期出候选用 turbo 快速筛，选定后再用完整 20 步重跑那一个镜头。
但这需要同一镜头两种设置各跑一次做画质对比，**目前还没做**，
不要在没对比的情况下直接全片用 turbo。

## 七、提交前后各查一次

**提交前**：

```bash
curl -s http://127.0.0.1:8188/queue
```

`queue_running` 非空说明有人在跑。这时候可以提交（会排队），
但**不要提交 R2V**——如果当前批次是 T2V/I2V，你一个 R2V 插进去，
会把整批的权重状态打乱。

**提交后**：

```bash
curl -s http://127.0.0.1:8188/history/<prompt_id>
```

确认三件事：`status.status_str == "success"`、
`outputs` 里有产物文件名、`execution_cached` 的节点数**不是全部**
（全部命中说明你的输入和上一次一模一样，拿回的是旧视频）。

然后把这一条登记进 `docs/task_registry.md`。
